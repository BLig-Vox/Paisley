# Browny Multi-tab Browser Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the Iced greeting with a working Rust GTK4/WebKitGTK multi-tab browser.

**Architecture:** A single GTK application owns a browser window. A notebook holds independently owned WebViews; weak signal captures avoid stale tab callbacks and reference cycles. URL normalization stays separate from the GUI for headless unit testing.

**Tech Stack:** Rust 2024, GTK4, WebKitGTK 6.0 API, gtk4/webkit6 Rust bindings, url.

**Spec:** `docs/superpowers/specs/2026-11-07-browser-design.md`

## Global Constraints

- Linux-first; 1280 × 800 default window.
- Preserve engine security defaults; do not install system packages or commit without permission.
- Local startup page; no startup network request.
- No persistent browsing-history UI, download manager, or session restore.

## Review Focus

- Background titles/URIs must never overwrite active-tab controls.
- Closing a tab during loading must not update another tab or leave retained WebViews.
- Closing the last tab must leave a usable welcome tab.
- Explicit unsafe schemes and malformed HTTP addresses must not execute or silently become searches.
- Local navigation failures must remain visible and not bypass TLS checks.
