# Paisley end-to-end investigation — 16 November 2026

Times are UTC; the session crossed midnight into 17 November in Asia/Manila.

## Scope and result

Tested latest source `5626c9f`, followed by the local bookmark-panel cancellation
fix in this working tree. The desktop binary reports package version 0.1.1;
crates.io 0.1.1 predates the latest source changes. No new crate or release was
published by this investigation.

The 71 Rust and 27 Python checks pass. A full graphical run passed, but later
repeats exposed intermittent cross-origin history/load timeouts. The latest
full repeat passed after strengthening committed-navigation preconditions;
the isolated boundary case passed too. This is **not** a claim that the earlier
flakiness is fully explained or eliminated.

No main-application crash or emergency memory cutoff occurred in the owned live
browsing/tab-cycle runs. However, the separately running original Gmail tab's
WebKit page process stopped during the investigation. Its exact termination
reason was not logged. The container reports `memory.max=max` and zero OOM kills,
so container OOM is not established. This background-page failure remains an
open reliability finding. This finite test does not prove absence of leaks.

YouTube playback is **not an unconditional pass**: a public video played in
Paisley to about 0:37 and then displayed “Something went wrong.” A fresh Firefox
profile on the same desktop also played the video and reached the same error.
This reproduces the failure outside WebKit, but does not establish its precise
network/site/media cause. A local MP4 played successfully in Paisley.

Servo 0.8.0 was tested as an unmodified, separate upstream demo runtime, with
multiple tabs sharing one engine process, one layout thread and two Rayon and
llvmpipe threads. It was **not integrated into Paisley**: the compatibility gate
failed before a backend migration was justified. Do not describe its partial
workload's lower RAM as a percentage saving for an equivalent working browser.

## Environment and measurement

- Ubuntu 24.04 Bot Screen, XFCE/X11, GTK 4.14.5, WebKitGTK 2.52.6.
- VNC reports DRI3 unavailable; software rendering affects these measurements.
- Fresh disposable normal profiles, no account credentials in test profiles.
  The user's Gmail/default profile stayed open and was excluded from the owned
  browser process group being measured.
- `/proc/*/smaps_rollup` PSS, RSS and swap sampled every two seconds for each
  owned browser process group. PSS is preferred; summed RSS double-counts shared
  pages. Per-process rows and global available memory were recorded.
- The application's PPid-tree counter and the external process-group sum have
  different coverage rules and sample times. They are estimates, not an exact
  whole-system/GPU allocation total.
- Emergency cutoff: owned browser PSS over 4,096 MiB or global available memory
  below 1,536 MiB. This was a sampled guard, not a kernel cap or a product budget.
- Test profiles, other test processes and shared libraries can affect PSS.
  Runs were sequentially staged and partially overlapped during idle periods;
  they are not a controlled cross-engine performance benchmark.

### Fixed and maintained tests

- **Real bug:** closing a bookmark sheet or its owning browser could leave a
  pending native import confirmation alive. Its cancellation previously waited
  for widget destruction, which can be delayed while callbacks hold references.
  Sheet unmapping now cancels its lifetime. The updated fixture reproduced the
  owner-close failure before the fix and passed normal/private cancellation
  checks afterwards.
- Tests previously searched for standalone bookmark/history windows, immediate
  bookmark creation, old button labels and old result-counter wording. They now
  operate on the sidebar, explicitly save drafts and scope searches to the panel.
- Advanced settings must be expanded before traversing their native controls.
- Download destination details now live in tooltips; the fixture verifies that
  metadata and the current “Show in folder” / “Clear history…” controls.
- Packaging assertions now require the shipped logo, URL placeholder and web
  scheme associations, and verify every archived payload's manifest hash.
- The old failure fixture used unsafe port 1. This WebKit converted that request
  to `about:blank` without the expected network-failure signal. The fixture now
  uses its owned server closing a connection before sending a response.
- One repeat timed out on Back to a site-exception origin; another timed out
  on the cross-origin destination. The fixture originally advanced after a
  request counter increment; it now additionally waits for committed history
  entries. A diagnostic-only boundary runner was added through
  `PAISLEY_BLOCKING_BOUNDARIES=1`. One isolated run and the latest full run passed.
  Repeated-run flakiness remains a limitation, not a proven production fix.
- GTK emits `gtk_widget_measure` / negative GtkImage allocation warnings on this
  runtime. A diagnostic `G_DEBUG=fatal-criticals` run therefore aborted. Normal
  runtime completes the fixture; **the underlying GTK layout warning remains**.

canvas 2D, WebAssembly, a worker, IndexedDB opening and service-worker registration.
These are targeted checks, not comprehensive Web Platform Tests. Japanese,
Chinese, Korean, Arabic, Hindi and emoji glyphs rendered visibly; IME composition
and all font variants were not tested.

Clicking native MP4 controls advanced playback; telemetry recorded 4.46 seconds
and 134 decoded frames before the five-second sample ended. Eight fixture tabs
per cycle each reported successful page execution through the local server.
Unsaved ASCII form text survived switching to and closing those tabs.

Public example.com, the Rust Book, Google search, the public Paisley repository
and the YouTube homepage rendered in Paisley. Google initially displayed a
traffic challenge and then rendered results without solving a challenge.
Public services can change their content, so those views are not deterministic
fixtures. No login or CAPTCHA was automated.

The initial public-tab peak was heavy, but post-close memory eventually returned
near baseline. Retention before the cleanup interval alone is not evidence of a
leak. The three cycle peaks rose modestly; the run also included a 48 MiB
allocation/release probe, page caches and different process lifetimes. Do not
infer a per-cycle leak rate from those peaks. A final recovery interval is
recorded in the accompanying summary: about 790 MiB remained after the extra media and last-tab replacement activity.

The last-tab replacement path was also exercised: closing the final tab creates
a new homepage tab. Consequently the final recovery is a reloaded fixture, not
the original document retaining the earlier unsaved form text.

The demo shell also left the previous URL in its address bar after closing back
to the first tab. That is an observed demo-shell UI issue; it is not a Paisley
regression and is separate from engine API compatibility.

Servo exposes optional IndexedDB and Service Worker preferences. A separate
throwaway run with `--pref=dom_indexeddb_enabled=true` and
`--pref=dom_serviceworker_enabled=true` passed both targeted API checks. GitHub
still produced the same `adoptedStyleSheets` errors with those flags enabled, and YouTube still failed with `client error (SendRequest)`.
Results are in the summary alongside the default run.

Servo offers embedding APIs and a GTK adapter, but Paisley's WebKit-specific
Inspector, sessions, cookie/storage controls, notifications, favicons, permissions
and download integration are not replaced by changing a Cargo dependency.
Sources: [Servo embedding guide](https://book.servo.org/),
[Servo GTK](https://github.com/nacho/servo-gtk),
[Servo 0.8.0 preferences](https://github.com/servo/servo/blob/v0.8.0/components/config/prefs.rs).

The default Servo runtime also completed three eight-tab fixture cycles without
an application crash. Peaks were approximately 1,266, 1,665 and 2,048 MiB PSS.
All eight distinct fixture URLs reported execution in each cycle. The first
local MP4 advanced to completion in Servo too. These results do not establish
an overall RAM advantage: the default storage features were unavailable, some
public content failed, and memory increased across these short cycles. After more than five minutes of final post-close observation, about 1,450 MiB remained. Final
post-close retention is recorded in the summary.
